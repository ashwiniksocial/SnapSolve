## C. Exact root cause(s) of Science’s 19–36 second behaviour

1. **Science is not taking a different or broken runtime route.**  
   All six Science questions used the intended bank fast path:
   `Practice click → Solution → bankContext → POST /api/solveQuestion/stream → streamed bank lesson`.

2. **Science IDs are not failing bank lookup.**  
   The Biology V2 adapter preserves the question ID. Its only relevant normalization is `ch01 → bio-ch01` for the chapter ID. The server logs show each Biology question ID being successfully cached after generation, proving `bankContext.questionId` reached the backend.

3. **No planner, reviewer, or improver is running for Science bank questions.**  
   The bank stream route explicitly skips blueprint planning and does not invoke the non-stream quality pipeline. There is one `gpt-4o-mini` streamed draft call per uncached Science question.

4. **The direct cause is larger grounded input plus substantially longer generated Detailed lessons.**  
   Every bank request includes the complete frozen answer, approved steps, concepts, hint, and the full eight-section Detailed lesson schema. Biology’s stored material is much larger:
   - Easy Biology answers: **416–611 characters**, versus Maths answers of **39–99 characters** in the actual browser run.
   - Biology Q73–Q75 answers: **2,052–3,302 characters**.
   - Biology Q73–Q75 bank grounding payloads: **3,136–4,577 characters**.
   - Biology Q73–Q75 then generate **2,250–2,402 completion tokens**.

5. **The logged timings match token generation, not a hidden extra API call.**  
   Science first content arrives consistently at **1.02–1.20 seconds**, but full lesson completion rises from **19.78–25.02 seconds** for easy questions to **32.40–35.81 seconds** for hard HOTS questions. This is direct evidence that the later time is spent completing the larger Detailed response.

## D. Exact explanation of IT Q50’s 1-second result

IT Q50 was **not** served by browser localStorage and **not** served by the server lesson cache.

The exact sequence was:

1. Browser sent `POST /api/solveQuestion/stream`.
2. The API rate limiter rejected it with **HTTP 429 in 3ms**.
3. The browser logged: `TeachingLesson generation failed: Error: rate_limit`.
4. `Solution.tsx` caught that streaming failure and immediately rendered the frozen bank fallback using the stored answer and approved steps.

So the 1-second result demonstrates the speed of the **frontend’s error fallback**, not a cached Detailed lesson. It is fast, but it is not the target complete Detailed teaching experience.

## E. Whether progressive content displays before DONE

**Yes. The frontend does display progressive content before `done`.**

- The server emits `section` events as fields are extracted.
- The client switches from the spinner to `SolutionCard` on the first `keyConcepts` or `step` event.
- `flushSync` forces that render immediately.
- The browser-visible first content is supported by telemetry at approximately **0.75–1.97 seconds** across the successful current runs.

However, the founder’s stopwatch aligns strongly with **full SSE completion / `done`**, not first content:

- Science Q1: observed 19s; server DONE 19.78s
- Science Q2: observed 24s; server DONE 22.80s
- Science Q3: observed 27s; server DONE 25.02s
- Science Q73: observed 35s; server DONE 33.49s
- Science Q74: observed 34s; server DONE 32.40s
- Science Q75: observed 36s; server DONE 35.81s

Therefore, the card appears progressively, but the perceived “answer generated” event is the point at which the full Detailed lesson is complete.

## F. SINGLE highest-impact next fix

**Pre-generate and persist the complete Detailed bank lesson for each frozen question before the student clicks it.**

This preserves:

- The existing model
- All eight visible Detailed teaching sections
- Existing question-bank content
- The same teaching quality
- The existing frontend renderer

It removes the first student’s need to wait for a full on-demand 1.2k–2.4k-token Detailed generation.

## G. Estimated effect of that single fix

For a pre-generated lesson:

- **Server-cache response:** demonstrated at **6ms** for the existing cached Maths request.
- **Browser local cache:** code path is synchronous localStorage retrieval and immediate render; the target is effectively instant.
- **Founder-observed first-use latency:** expected to drop from the current **15–36 seconds** of on-demand generation to approximately **1–4 seconds end-to-end**, with the residual time being route/session/render work rather than model generation.
- **Repeat local-cache latency:** under the existing design, approximately **sub-second**.
